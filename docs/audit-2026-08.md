# Design, UX, IA & Engineering Audit

_markfasel.com · audited 2026-08-06 · branch `refresh-branding` @ b0485ba_

**Framing:** this audit assumes the site is the long-term foundation for a personal
brand, a publishing operation, and a consulting business — not a one-time portfolio
launch. Recommendations optimize for maintainability, content velocity, lead
generation, and premium positioning, in that order.

**Verified state:** `pnpm typecheck`, `pnpm lint`, and `pnpm build` all pass clean.
The build emits **4 routes**: `/`, `/_not-found`, `/experience`, `/styleguide`.
Everything below is measured against that, not against the docs.

---

## 0. Executive summary

The design system foundation is genuinely good. Tokens are complete and disciplined,
the brand voice is consistent, the diagram work is real, and the accessibility
instincts (focus rings, focus trap, reduced-motion, skip link, semantic lists) are
better than most production sites. Two pages are built to a high standard.

Three things will hurt if you build more pages before fixing them:

1. **The site is a shell with no exits.** Every primary nav item except Experience
   is a 404. The homepage's final call-to-action sends visitors to LinkedIn.
2. **The styling approach doesn't scale.** ~130 inline `style={{}}` blocks and a
   `globals.css` that has absorbed 250+ lines of page-specific CSS. There is no
   `<Section>`, `<Container>`, `<Card>`, or `<Button>` primitive — the same section
   shell is copy-pasted ten times. Each new page compounds this.
3. **Zero SEO/AI-search infrastructure.** No sitemap, robots, RSS, `llms.txt`,
   JSON-LD, canonicals, or OG images. For a business whose distribution model is
   "publish essays, get found," this is the load-bearing gap.

Everything else is downstream of those three.

## Phase 1 — Global audit

### P0 — Blocks launch

#### 1.1 Every primary navigation link is a 404

**Problem.** `lib/nav.ts` defines `/about`, `/experience`, `/work`, `/writing`,
`/consulting`, `/products`, `/contact`. Only `/experience` exists. The dead links
are rendered by `Header`, `MobileDrawer`, `Footer`, the Hero's secondary CTA
(`/contact`), and `ExperienceLinks`' primary orange CTA (`/contact`).

**Why it matters.** Every conversion path on the site terminates in a 404. There is
also no custom `not-found.tsx`, so visitors hit the default Next.js error page —
unbranded, no navigation, no recovery. A buyer who clicks "Let's talk →" and lands
on a stock 404 is gone.

**Recommendation.** Before any polish work: ship a branded `app/not-found.tsx`, then
either build the routes or gate `NAV_LINKS` behind a `published` flag so unbuilt
routes don't render. I'd do both — the flag is 10 lines and protects you every time
you add a nav item ahead of a page.

**Priority: P0.**

#### 1.2 No SEO, syndication, or AI-search infrastructure

**Problem.** Missing entirely: `app/sitemap.ts`, `app/robots.ts`, `rss.xml`,
`feed.json`, `llms.txt`, `llms-full.txt`, JSON-LD on any page, canonical URLs, and
OG images. `app/layout.tsx` declares `openGraph` but supplies no `images`, so every
LinkedIn/X/Slack share renders a blank card.

**Why it matters.** The brand spec correctly identifies AI search as load-bearing
for 2026 buyer discovery. None of it exists. And the single highest-ROI item —
an OG image — is currently a blank rectangle on the exact channel (LinkedIn) that
is your primary distribution surface.

**Recommendation.** `lib/seo.ts` + per-route `generateMetadata` + a dynamic OG route
using `next/og` (built into Next 16 — no `@vercel/og` dependency needed). Then
sitemap/robots, then JSON-LD, then `llms.txt`. Detail in Phase 6.

**Priority: P0.**

#### 1.3 The homepage has no conversion path

**Problem.** Homepage composition is: `Hero → TrustBar → ArchitecturePhilosophy →
ExperienceTimeline → IndustriesGrid → ExperienceMore`. It ends on `ExperienceMore`,
whose only action is an outbound `target="_blank"` link to LinkedIn.

Missing versus the brand spec's own wireframe: services/consulting section, case
studies section, products, writing preview, newsletter capture, closing contact CTA.

**Why it matters.** The last thing a visitor can do on your highest-traffic page is
leave for someone else's platform. There is no email capture anywhere on the site,
which means every visitor is a one-time visitor. For a brand whose compounding asset
is a newsletter list, this is the most expensive single gap on the site.

**Recommendation.** Add, in order of value: (a) a closing `Let's talk` CTA section,
(b) newsletter capture, (c) a consulting/services section, (d) writing preview.
Demote the LinkedIn link from "final action" to a secondary link.

**Priority: P0.**

#### 1.5 793KB unoptimized `priority` image on `/experience`

**Problem.** `ExperiencePortrait` renders `<Image unoptimized priority>` against a
793KB PNG. The code comment states AVIF strips the alpha channel. That's incorrect —
AVIF supports alpha. The original failure was almost certainly lossy WebP (VP8),
which does drop alpha; `next.config.ts` now sets
`formats: ['image/avif', 'image/webp']` to fix exactly that — but `unoptimized`
bypasses the entire pipeline, so **that config change currently does nothing.**

Additionally `public/images/mark-fasel-portrait_original.png` (1.0MB) is tracked in
git and served from `/public` though nothing references it.

**Why it matters.** This is in the LCP region of `/experience`. 793KB blows the
≤1.2s LCP budget on anything short of good broadband, and it's `priority`, so it
competes with fonts for early bandwidth. The site's stated Lighthouse floor is 98.

**Recommendation.** Remove `unoptimized` and re-test — AVIF should preserve the
cutout. If it doesn't, the fix is a lossless/alpha-preserving encode at build time,
not shipping a raw PNG. Delete `_original.png` from the repo. Verify with the actual
served bytes, not the config.

**Priority: P1.**

#### 1.6 The homepage timeline is out of chronological order

**Problem.** `content/experience/timeline.json`, rendered live on the homepage:

```
Life Surge / Oxlos          Oct 2025–Present
Roghnu                      Jan 2025–Oct 2025
Scorpion                    Nov 2020–Oct 2024
Ramsey Solutions            May 2018–Jan 2019   ← out of order
Publix Super Markets        Apr 2019–Nov 2020   ← should precede Ramsey
Independent Consulting      2005–Present        ← stranded mid-list
Johns Hopkins All Children's Aug 2014–May 2018
```

**Why it matters.** A recruiter reading a solutions architect's timeline and finding
it mis-sorted draws exactly the wrong conclusion about attention to detail. The
"Independent Consulting 2005–Present" entry buried between two W-2 roles also buries
the single most commercially relevant fact on the page — that you've been consulting
for twenty years.

**Recommendation.** Sort reverse-chronologically by end date. Pull "Independent
Consulting" out of the sequence entirely and treat it as a persistent parallel track
(a spanning rail, or a separate framed statement above the timeline) — it's a
different _kind_ of entry and shouldn't compete positionally with employment.

**Priority: P1 — content correctness, ~15 minutes.**

#### 1.7 "Trusted by organizations including" over a list of employers

**Problem.** `TrustBar` labels LifeSurge, Ramsey, Johns Hopkins, Publix, and Scorpion
as organizations that "trust" you. These are former employers, not consulting clients.

**Why it matters.** For the recruiter audience it reads fine. For the consulting
buyer — the #1 priority audience per the brand spec — it implies a client roster you
don't have. That's a real credibility exposure the moment you sell services on the
same page, and it's the kind of thing a sophisticated buyer checks.

**Recommendation.** Change the label to something factually exact and equally strong:
"Twenty years across" or "Systems built for" or "Experience includes". Costs nothing,
removes the exposure. Reserve a true "Selected clients" bar for the consulting page
once you have clients to name.

**Priority: P1 — one line of copy.**

#### 1.8 Mobile section rhythm is 16px

**Problem.** `--section-py` is `var(--space-4)` (16px) on mobile, `var(--space-7)`
(48px) at 768px, `var(--space-11)` (192px) at 1024px. The brand spec calls for
96px mobile / 160px desktop.

**Why it matters.** 16px of vertical padding is roughly a paragraph gap. On a phone
the sections will visually run together into one continuous stack — the exact
"generic blog" failure mode CLAUDE.md is built to prevent. It's also a 12× jump
between the smallest and largest breakpoint, which no amount of design can make feel
like one system.

**Recommendation.** Move to something like 64px → 96px → 160px. If desktop 192px was
a deliberate editorial choice, keep it, but mobile needs to be at least 56–64px.
Worth reviewing on a real device before locking.

**Priority: P1.**

#### 1.9 Repo hygiene

Tracked in git and shipped to `/public` despite being unused: `next.svg`,
`vercel.svg`, `file.svg`, `globe.svg`, `window.svg` (create-next-app leftovers),
`mark-fasel-portrait_original.png` (1.0MB). Also `src/` exists containing only a
`.DS_Store` (untracked — `.gitignore` covers it — but the empty directory is
confusing given `CLAUDE.md` specifies a no-`src` layout).

**Priority: P2 — 5 minutes, do it during the next cleanup pass.**

## Phase 3 — Design system audit

### 3.1 The system is inline-style driven, not utility driven

**Problem.** ~130 `style={{}}` blocks across components (plus 158 in the styleguide).
Tailwind is used only for layout scaffolding (`grid`, `flex`, `mx-auto`,
`lg:grid-cols-2`); every color, space, border, and radius is an inline CSS variable
reference.

**Why it matters.** Three concrete consequences, all already visible:

1. **No responsive variants.** You cannot write `md:padding` in an inline style. This
   is why `globals.css` has absorbed 250+ lines of page-specific CSS (`.exp-hero`,
   `.exp-portrait-*`, `.exp-entry--left`, `.exp-line`). Layout logic for one page now
   lives in a global stylesheet, far from the component that owns it.
2. **No hover/focus states.** Also impossible inline — which is why `.cta-primary`,
   `.cta-ghost`, `.cta-text`, and `.nav-link` are global classes instead of component
   variants.
3. **Tooling is inert.** `prettier-plugin-tailwindcss` and `tailwind-merge` are
   installed and do almost nothing, because there are barely any utility classes to
   sort or merge.

Token _purity_ is excellent and should be preserved. The problem is the delivery
mechanism, not the discipline.

**Recommendation.** Tailwind v4 generates utilities from `@theme` automatically —
`--color-accent` already yields `text-accent`/`bg-accent`/`border-accent`, and
`--space-5` yields `p-5`-style utilities. Migrate to those. Reserve inline styles for
genuinely dynamic values (the `--hero-delay` stagger, computed percentages). Keep
`globals.css` for genuinely global concerns only.

This is the **single highest-leverage refactor available** and it gets more expensive
with every page added.

**Priority: P1 — do it before building the remaining six pages, not after.**

### 3.2 Missing layout primitives — the section shell is copy-pasted 10×

Every one of these repeats the identical block:

```
mx-auto · maxWidth: var(--container-default) · paddingInline: var(--container-gutter)
paddingBlock: var(--section-py) · borderTop: hairline solid var(--color-border)
```

`ArchitecturePhilosophy`, `ExperienceTimeline`, `IndustriesGrid`, `ExperienceMore`,
`ExperienceCompetencies`, `ExperienceCareer`, `ExperiencePrinciples`, `SelectedWork`,
`ExperienceRecommendations`, `ExperienceLinks`, `TrustBar`.

**Recommendation.** Build three primitives and migrate all eleven:

- `<Container>` — max-width + gutters. One place to change container behavior.
- `<Section>` — `<Container>` + section padding + optional top divider + optional
  `id` for anchoring/ReadingProgress.
- `<SectionHeader label title lead>` — the `SectionLabel → h2 → lead paragraph`
  triple that appears in 9 of 11 sections with slightly different spacing each time.

**Priority: P1.**

### 3.3 Missing content primitives — real inconsistency already present

| Pattern                 | Appears in                                                                                                      | Drift                                                      |
| ----------------------- | --------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| Bordered flat card      | ArchitecturePhilosophy, ExperiencePrinciples, SelectedWork, ExperienceRecommendations                           | padding varies: `space-6`, `space-6`, `space-7`, `space-7` |
| "— outcome" bullet list | ExperienceCareer, SelectedWork                                                                                  | identical markup, duplicated                               |
| Tech chip row           | ExperienceCareer, SelectedWork                                                                                  | labeled "Technologies" vs "Stack"                          |
| Mono index + label      | ArchitecturePhilosophy (`01` hardcoded), ExperiencePrinciples (`padStart`), ExperienceCompetencies (`padStart`) | three implementations of the same thing                    |

**Recommendation.** `<Card>`, `<Chip>`, `<OutcomeList>`, `<IndexedItem>`. Pick one
label for the chip row and use it everywhere.

**Priority: P1.**

### 3.4 There is no Button component — and three different button sizes already exist

`.cta-primary` / `.cta-ghost` / `.cta-text` are global CSS classes with padding
passed inline at each call site:

| Call site         | Padding                   |
| ----------------- | ------------------------- |
| `Hero`            | `space-4 space-6` (16/32) |
| `ExperienceLinks` | `space-3 space-5` (12/24) |
| `Header`          | `space-2 space-4` (8/16)  |

**Why it matters.** Three sizes, no size scale, no shared component — so nothing
stops the fourth from being different again. The contact form, consulting CTAs, and
newsletter form are all about to need buttons.

**Recommendation.** Build `<Button variant="primary|ghost|text" size="sm|md|lg" asChild>`.
CLAUDE.md already specifies shadcn's Button for exactly this and it was never
installed — either install and restyle it, or hand-build to the same API. Given how
token-pure everything else is, hand-building is defensible and avoids a Radix
dependency; either way, **decide and document it**, because the current state is
"the docs say shadcn, the code says global CSS classes."

**Priority: P1 — blocking the contact form.**

### 3.5 Two near-duplicate label components

`EyebrowLabel` (24px orange divider, accent text default) and `SectionLabel` (12px
muted tick, muted text default) are the same component with different tick widths
and defaults. Both are `type-mono-label inline-flex items-center` with a leading rule.

**Recommendation.** One component, two variants (`eyebrow` | `figure`). Preserve the
rule that the eyebrow divider is always orange — that's a real brand constraint,
correctly enforced today.

**Priority: P2.**

### 3.6 Zero state coverage

No loading, skeleton, empty, error, disabled, or success states exist anywhere. This
is expected — no forms or async data yet — but it becomes P0 the moment the contact
form lands, and `/writing` and `/work` will both need empty states on day one.

**Recommendation.** Add a "States" section to the styleguide as part of the contact
form work, covering: button (default/hover/focus/active/disabled/loading), input
(default/focus/error/disabled), form (idle/validating/submitting/success/error),
and list (populated/empty).

**Priority: P1 — concurrent with the contact form.**

### 3.7 Card hover and interaction affordances

`SelectedWork` and `ExperienceCareer` render "Read the case study →" as a raw `<a>`
(not `next/link`), the card itself isn't interactive, and there's no hover state.
Once these point at real case studies, the whole card should be the target with a
clear hover treatment (border → `border-strong`, or the title → accent).

**Priority: P2 — but design it now, before `/work` is built on top of it.**

### 3.8 Hardcoded values that should be tokens

| Value                     | Location                              | Notes                                      |
| ------------------------- | ------------------------------------- | ------------------------------------------ |
| `fontSize: 17`            | `TrustBar`                            | between `body-lg` (19) and `body` (16)     |
| `fontSize: 22`            | `MobileDrawer`                        | nav item size — no token                   |
| `fontSize: 12`, `13`      | `TopologyHero`                        | diagram labels — no token                  |
| `maxWidth: '640px'`       | `ExperienceMore`, `.exp-hero-content` | measure — no token                         |
| `rgba(255,255,255,.08)`   | `ExperiencePortrait` (×6)             | **hardcoded white — breaks in light mode** |
| `rgba(245,242,235,0.025)` | `.exp-hero-ghost`                     | hardcoded text color                       |
| `rgba(18,18,18,…)`        | `.exp-portrait-vignette`              | hardcoded surface color                    |

**Recommendation.** Add the missing type tokens; convert the `rgba()` values to
`color-mix(in oklab, var(--color-text) 8%, transparent)` — the pattern `GridOverlay`
already uses correctly.

**Priority: P2.**

### 3.9 Section-label numbering doesn't scale

Home uses `ARCH.01, EXP.01, EXP.02, EXP.03`. `/experience` uses `EXP.00, EXP.01,
ARCH.02, WORK.01, EXP.04, EXP.05`. `EXP.01` appears on both pages meaning different
things; `ARCH.01` and `ARCH.02` are split across two pages.

**Why it matters.** The scheme reads as a single global sequence but is maintained
by hand per-page. Inserting a section anywhere implies renumbering everywhere, and
it's already inconsistent with only two pages built. Across ten pages it will be
unmaintainable, and the drafting-annotation effect only works if it looks systematic.

**Recommendation.** Make it per-page and derive it: each page declares a prefix
(`HOME`, `EXP`, `WORK`, `CONS`), and `<Section>` auto-numbers within the page. Or
drop the numbers and keep the labels semantic (`ARCHITECTURE`, `SELECTED WORK`).
The second is less clever and ages better.

**Priority: P2 — decide before six more pages bake it in.**

### 3.10 Dead code

- `ReadingProgress` — fully built and documented, imported nowhere (not even the
  styleguide). It was designed for `/experience`; either wire it up or delete it.
- `GridOverlay` — used only by the styleguide's `?grid=1`. Its docblock describes an
  "ambient" mode for page backgrounds that no page uses.

**Priority: P3.**

### 3.11 What's genuinely good (don't regress these)

- **Token completeness.** Every color, type, space, radius, and stroke value in the
  brand spec is in `tokens.css`, with the light-mode preview correctly scoped to
  `[data-mode='light']`.
- **Accessibility instincts.** Skip link as first focusable element; a hand-rolled
  focus trap in `MobileDrawer` with Escape, scroll lock, and focus restoration;
  `role="img"` + `<title>`/`<desc>` on diagrams; `useId()` for SVG ids so duplicate
  instances don't collide; `sr-only` "(opens in a new tab)" on external links;
  semantic `<ol>`/`<figure>`/`<blockquote>`.
- **Reduced motion.** Handled correctly — animation is additive inside
  `prefers-reduced-motion: no-preference`, so reduced-motion users get the final
  state rather than a suppressed animation.
- **The `--color-on-accent` token.** Correctly solves the orange-button contrast
  problem the brand spec identified (white-on-orange fails at 3.1:1).
- **The styleguide's computed WCAG grades.** Contrast is calculated, not asserted.
- **The comments.** Genuinely high signal — they explain _why_, including rejected
  alternatives. Preserve this convention.

## Phase 4 — Information architecture

Current primary nav: **About · Experience · Work · Writing · Consulting · Products**

- `Let's talk →`. Footer: the same six + Contact.

### 4.1 Experience and Work are the same page to a visitor

`/experience` already contains `ExperienceCareer` — headlined **"The career, as case
studies"** — _and_ `SelectedWork` — headlined **"Selected work."** If `/work` is also
case studies, you have two case-study pages and a visitor has no way to predict
which one to click.

**Recommendation.** Enforce a hard distinction:

- **`/experience`** = the career record. Recruiter-optimized, scannable, role by role,
  résumé download. One job.
- **`/work`** = deep case studies. Problem → constraints → architecture → tradeoffs →
  outcome → lessons. Buyer-optimized. Each becomes its own page.

That means moving `SelectedWork` off `/experience` (or reducing it there to a
three-item teaser linking to `/work`).

### 4.2 Six nav items plus a CTA is one or two too many

Every reference brand in your list runs 4–5 primary items. More items means smaller
type, less whitespace, and a nav that reads as a sitemap instead of an argument.
`Products` currently points at a page with zero products — a nav item that leads to
an empty room costs more credibility than it buys.

**Recommendation.**

```
Work · Writing · Consulting · About        [ Let's talk → ]
```

Rationale: `Work` and `Writing` are the proof surfaces both audiences need.
`Consulting` is the buyer path. `About` is the human path and the natural parent for
`/experience`. `Experience` moves to a prominent link on `/about` plus the footer —
recruiters who want it will find it, and it's still directly linkable from LinkedIn.
`Products` stays out of the nav until one ships.

If you'd rather keep `Experience` in the nav (defensible — it's your strongest page
and recruiters are a real audience), drop `Products` and run five.

### 4.3 The footer should be a site index, not a nav repeat

Currently `FOOTER_NAV_LINKS` = primary nav + Contact, in one 2-column grid. On a
publication, the footer is where the long tail lives and where audiences self-sort.

**Recommendation.** Three or four labeled columns:

```
WORK            WRITING           ABOUT             CONNECT
Case studies    All essays        About             Let's talk
Consulting      Architecture      Experience        Newsletter
Products        AI                Résumé            LinkedIn
                Leadership        Now               GitHub
```

## Phase 5 — Plan for the remaining pages

### `/about`

**Purpose.** The trust page. Both audiences land here second. It answers "who is this
person and why should I believe them," which is a different question from "what have
they done" (`/experience`) or "what do they sell" (`/consulting`).

**Sections.**

1. Hero — portrait + positioning statement. First paragraph must be a structured

2. The narrative — how you got here, in first person. This is where the serif and

3. Engineering philosophy — how you think about systems. Should read as conviction,
   not a values list.
4. Leadership philosophy — how you work with teams and executives.
5. Timeline preview — 5 entries, links to `/experience`.
6. Current focus — what you're working on now. Links to `/now`.
7. Photography moment — this is one of the three places the imagery diet allows it.
8. FAQ — "What does a solutions architect actually do?", "What do you consult on?",
   "Are you available?" Carries `FAQPage` schema and captures Tier 3 keywords.
9. CTA — split: `Let's talk` (buyer) and `View experience` (recruiter).

**Schema.** `Person` + `ProfilePage`. This is the page that teaches ChatGPT and
Perplexity who you are.

**Note on faith framing.** The brand spec calls for it. It's your call and it's a
positioning decision, not a design one — it will resonate strongly with part of your
buyer market (LifeSurge is in that world) and be neutral-to-negative with another

standalone section, so it reads as _who you are_ rather than as a filter.

### `/work`

**Purpose.** Proof. Not a gallery — a set of arguments about judgment.

**Index page.** Filterable by domain and by capability. Each card: client/context,
title framed as a _problem_, one-line outcome with a number, 2–3 tags, custom
diagram thumbnail. Alternating layout per the brand spec.

**Case study template** — this structure is the product:

1. Header — client, role, timeframe, stack
2. The problem — what was actually broken, with numbers
3. Constraints — what you couldn't change. This is the section that proves seniority
4. The architecture — the diagram. This is the page's centerpiece
5. Key decisions and tradeoffs — what you chose _against_ and why
6. Outcome — measured, specific
7. What I'd do differently — the most credible section on the page
8. Related — 2 other case studies + 1 essay
9. CTA — `Let's talk`

**Content reality check.** You currently have four `work.json` entries with empty
outcomes and no case-study bodies. **Two excellent case studies beat six thin ones.**
Recommend launching with two written in full (Pentastar/Sage Intacct integration and
the LifeSurge platform ecosystem read as the strongest), and listing the rest as
timeline entries on `/experience` rather than as stub cards.

**Confidentiality.** Check what you can name. Where you can't, "a national retail
platform" plus real numbers is more credible than a logo plus vague claims.

### `/writing`

**Purpose.** The compounding asset. This is the SEO engine, the AI-search surface,
and the newsletter's top of funnel.

**Index.** Featured essay (large) + reverse-chron list. Filter by pillar. Reading
time. Pillar landing pages as cluster hubs.

**Essay template.** ArticleHeader (pillar, date, reading time) · optional drop cap ·
prose with `PullQuote` / `Callout` / `Diagram` / `Stat` / `Aside` · TOC in the left
gutter on large desktop (this is what `ReadingProgress` was built for) · related
essays · newsletter CTA.

**Infrastructure needed.** `next-mdx-remote`, `shiki`, `remark-gfm`, `rehype-slug`,
and `rehype-autolink-headings` are **already installed and entirely unused.** The
pipeline is `lib/mdx.ts` + Zod frontmatter schemas + `MDXComponents` — roughly a
day's work, and it unblocks both `/writing` and `/work`.

**Search.** Not needed at launch. Below ~30 essays, pillar filtering plus browser
find is enough. Add Pagefind (build-time, static, no runtime dependency) when the
archive justifies it.

**Newsletter.** `lib/nav.ts` points at Substack. Decide: Substack-hosted (fast, but
you don't own the list surface or the design) vs. Resend + Supabase (own it end to
end, matches "premium," more work). Given the consulting business is the goal, I'd
own the list — but starting on Substack and migrating is legitimate. Either way, put
an email capture on the site now.

**Launch content.** 3 essays minimum, one per pillar, to establish range. The brand
spec's 12-essay calendar is a good source.

### `/consulting`

**Purpose.** The revenue page. This is where the positioning tension is sharpest —
your target list spans small businesses/trades/restaurants/medical offices _and_
growing companies/agencies. Those buyers do not respond to the same page.

**The tension, stated plainly.** A restaurant owner and a VP Engineering at a $200M
company are not the same buyer, and a page that speaks to both convincingly is very
hard to write. The brand spec assumes the enterprise buyer. Your prompt adds the SMB
segment. My recommendation: **lead with the outcome, segment by problem, not by
company size.** "Work that shouldn't be manual anymore," "Systems that stopped
scaling," "AI that actually ships" — these read the same to both buyers, and the
engagement models below them can differ.

**Sections.**

1. Positioning statement — what you do, declaratively. First paragraph is the summary
2. Problems you solve — 4–6, framed as the buyer's symptom, not your service name
3. Services — Architecture · AI Strategy & Automation · Internal Tools & Custom
   Software · Frontend Modernization · Fractional Architecture/CTO · Advisory.
   Each links to `/consulting/[service]`
4. How engagements work — discovery → assessment → roadmap → build/advise. Named,
   scoped, with a clear first step. Premium consulting sells _process_ legibility
5. Proof — 2–3 case studies pulled from `/work`
6. Who this is for / who it isn't. **Saying who you don't work with is the single
   strongest premium signal on a consulting page**
7. FAQ — pricing model, engagement length, remote/onsite, how to start. `FAQPage` schema
8. CTA — `Let's talk`

**Positioning guardrails.** No hourly rates. No "packages" with prices. No
"available for hire." Lead with engagement models, not deliverables. The brand spec's
"lead with capability, not availability" applies most strictly here.

**Service detail template.** Problem → approach → what you get → engagement shape →
relevant case study → FAQ → CTA.

### `/products`

**Purpose.** Placeholder that builds an audience, not a store.

**Recommendation.** One page, no `[slug]` routes, no ecommerce, no Stripe. Structure:
positioning statement ("what I'm building"), 2–4 products with honest status badges
(Live / Beta / In development), and — the actual point — an email capture: "Get
notified when these ship." That list is the asset.

**Keep it out of the primary nav until something is Live.** Footer link only.

### `/contact` — "Let's talk"

**Purpose.** The conversion page. Everything else funnels here.

**Recommended architecture** (this is the cleanest option for your stack):

```
app/(marketing)/contact/page.tsx     Server Component — copy, channels, form island
  _components/ContactForm.tsx        'use client' — react-hook-form + zodResolver
  actions.ts                         'use server' — validate, rate-limit, send
lib/schemas/contact.ts               Zod schema — imported by BOTH client and server
```

**Why Server Action over an API route.** One schema, imported by the resolver and
re-validated server-side; no fetch boilerplate; no public endpoint to abuse; progressive
enhancement for free. `useActionState` gives you idle/pending/success/error states
directly, which is exactly the state matrix §3.6 says is missing.

**Fields.** Name · Email · Company · Role · Project type (select) · Budget range
(select) · Timeline (select) · Message. Budget range is a qualification tool and a
premium signal — keep it, make it optional, and include an "I'm not sure yet" option
so you don't lose good leads who haven't scoped it.

**Spam protection.** Honeypot field + submission-timing check + server-side rate
limit by IP. **Do not add reCAPTCHA or Turnstile** — a third-party script violates
the "zero third-party scripts on critical pages" rule and would put a Google request
on your highest-value page. Honeypot plus timing stops the overwhelming majority of
bot traffic on a site this size.

**Delivery.** Resend → notification to you + auto-reply to sender (the auto-reply is
a premium signal and sets response expectations). Verify your sending domain with
SPF/DKIM before launch or you'll land in spam.

**Storage.** **Start without Supabase.** Resend plus your inbox is a complete system
at launch volume, and it's one fewer dependency, schema, and secret. Add Supabase
when you actually want to query leads — which is a real need, just not a launch need.
This is a deliberate deviation from the brand spec and I'd make it consciously.

**Accessibility.** Labels (not placeholders) on every field, `aria-describedby` for
errors, `aria-invalid`, `role="alert"` on the error summary, focus moves to the first
error on failed submit, success announced to screen readers.

**Also on the page.** Direct email, LinkedIn, GitHub, and — if you want inbound
booking — Calendly. **Embed nothing.** A Calendly iframe is a heavy third-party
script; link out to it instead.

## Phase 6 — Engineering recommendations

### 6.1 Folder and component organization

`components/marketing/` currently holds 15 files mixing homepage sections, experience
page sections, and shared pieces. `ExperienceHero` lives in `marketing/` while
`ExperiencePortrait` lives in `experience/`.

**Recommended:**

```
components/
  ui/            Button, Input, Textarea, Select, Card, Chip, Badge   ← primitives
  layout/        Container, Section, SectionHeader, Grid
  brand/         Logo, Wordmark, Submark, EyebrowLabel, GridOverlay
  diagrams/      TopologyHero, SystemDiagram, CriticalPath
  content/       MDXComponents, PullQuote, Callout, ArticleHeader, CodeBlock
  navigation/    Header, Footer, MobileDrawer, ReadingProgress
  sections/      Reusable across pages: NewsletterCTA, ContactCTA, CaseStudyCard

app/(marketing)/experience/_components/    Page-specific sections
app/(marketing)/page-sections/             Homepage-specific sections
```

Rule: if it's used on exactly one page, co-locate it under that route in
`_components/`. If it's used twice, promote it to `components/sections/`.

### 6.2 Content strategy

**MDX** for essays and case studies — long-form prose with embedded components.
Already installed, not yet wired. Build `lib/mdx.ts` + `lib/content-schemas.ts`.

**JSON** for structured, repeating, non-prose data — timeline, services, FAQs.
Current usage is right, but the parsing isn't:

```ts
const CAREER = careerData as CareerEntry[]; // ← unchecked cast
```

`noUncheckedIndexedAccess` is enabled and then defeated by the `as`. A typo in
`career.json` becomes a runtime crash instead of a build failure. **Parse with Zod
at module load** — malformed content then fails `pnpm build`, which is exactly where
you want to find it.

Also: `timeline.json` is derivable from `career.json` (it's the same data, fewer
fields). Derive it — two files that must stay in sync will drift, and they already
disagree in ordering (§1.6).

**No CMS.** Correct call, per CLAUDE.md. File-based MDX in git is the right system
for a single-author publication, and it keeps content in code review.

### 6.3 SEO implementation

```
lib/seo.ts                    buildMetadata({ title, description, path, image, type })
lib/schema.ts                 JSON-LD builders — Person, Article, FAQPage, Breadcrumb
app/sitemap.ts                generated from the MDX collections
app/robots.ts
app/rss.xml/route.ts
app/feed.json/route.ts
app/llms.txt/route.ts
app/llms-full.txt/route.ts
app/api/og/route.tsx          next/og — built into Next 16, no extra dependency
app/not-found.tsx             branded 404
```

Every page gets a canonical URL. Every page exports `generateMetadata`. Every essay
gets `Article` schema; `/about` gets `Person` + `ProfilePage`; root gets
`Organization` + `WebSite`; consulting service pages get `FAQPage`.

### 6.4 Performance

Currently sound: everything static except `/styleguide`, inline SVG diagrams, one
client component (`MobileDrawer`), self-hosted fonts with sensible preloads, no
third-party scripts.

Fix: the portrait image (§1.5). Delete unused public assets (§1.9). Make
`/styleguide` static by moving the grid toggle off `searchParams`.

Guard: **add a Lighthouse CI check** on `/`, `/experience`, and — once built —
`/writing/[slug]` and `/contact`. Budgets are already documented and currently
unenforced; the portrait regression is exactly what CI would have caught.

Watch: PostHog (load after `requestIdleCallback`, per CLAUDE.md), and any Calendly
embed (don't — link out).

### 6.5 Code splitting

Not currently a problem — nearly everything is a Server Component. The things that
will need attention: the contact form (client island, keep it scoped to the form,
not the page), and Motion (installed at v12, currently unused — all animation is CSS.
**That's the better choice.** Keep it CSS-only and consider dropping the dependency
unless a specific interaction genuinely needs it).

### 6.6 Testing

CLAUDE.md promises `pnpm test` with Vitest. Nothing exists.

**Recommendation.** Don't build a broad unit-test suite for a marketing site — the
ROI isn't there. Do add:

- **Zod schema tests** for content parsing (cheap, catches real content bugs)
- **One Playwright smoke test** — every route renders, nav links resolve, form submits.
  This would have caught the 404 nav on day one.
- **`axe-core` in CI** on the built pages.

Then either implement it or remove the promise from CLAUDE.md. A doc that describes
tests you don't have is worse than no doc.

### 6.7 Localization

Explicitly out of scope in PLAN.md and I agree. The one cheap habit worth keeping:
content in JSON/MDX rather than hardcoded in JSX. You're already doing this for
career and work data; extend it to services and FAQs. That's the 90% of the work if
you ever do localize, and it's good practice regardless.
